## Key Learnings

- **A duplicated ADR number makes every bare reference ambiguous — disambiguate by sense, never by `sed`.** When `0041`/`0042` were each used twice, ~40 bare `ADR-00NN` references split across two unrelated meanings in the same files (and sometimes the same crate). The reliable discriminators were (a) surrounding identifier context — every `ADR-0041` inside a `TRUSTED_BOOT_*` doc comment was the trusted-boot ADR — and (b) cross-checking cited sub-parts: "Decision #4" existed only in the five-decision trusted-boot ADR, not the three-decision imagebuilder one. Rule for renumbering: keep the number on the **earlier-dated Accepted** file, which also tends to preserve the most existing citations. Verify afterwards by censusing BOTH old and new numbers file-by-file, not by trusting the replace count.
- **Hand-editing a generated CRD YAML is only safe if the generator is re-run to prove zero drift.** An ADR reference lives in a Rust doc comment that `crdgen` copies into `deploy/crds/*.yaml`. Editing both by hand happened to match exactly, but that was only *known* after regenerating and diffing. `docs/src/reference/api.md` and `docs/src/architecture/flows.md` are likewise generated (from CRDs and from the CALM model) — edit the source, then regenerate.

- **Three overlapping instruction sources, and which wins.** `.claude/rules/*` (binding, current) > `docs/adr/` (canonical decisions) > `.github/community/` roadmaps (intent, often stale) > `01-DECISIONS.md` (pre-ADR history). When two disagree, the rules file and the ADR win; fix the roadmap rather than following it. Roadmap docs 00/01/02 were written at Phase 0 and are the most likely thing in the repo to be wrong about the current tree.
- **[2026-09-07] Verifying container base images without a container runtime.** Registry v2 API + anonymous bearer token + `tar -xzf` on the layer blobs reads `/lib/apk/db/installed` (apk) or `/var/lib/dpkg/status.d/` (dpkg) directly — this is how the Chainguard bump was confirmed to carry glibc 2.44-r5 before committing. Same trick resolves current digests for a pinned tag. Never start Docker Desktop just to inspect an image.
- **[2026-09-07] GitHub's code-scanning dismissal API caps `dismissed_comment` at 280 characters** (HTTP 422 above that), and an already-dismissed alert returns HTTP 400 on a second PATCH — reopen with `{"state":"open"}` first, then re-dismiss. Reasons are exactly `false positive`, `won't fix`, `used in tests`. Put the short version on the dashboard and the full argument in the CHANGELOG.

- **Project:** banlieue
- **Description:** A Kubernetes-native abstract virtualization API. Users create `VirtualMachine` CRs; controllers schedule them onto vSphere / Proxmox / libvirt backends via provider-specific infrastructure CRDs that satisfy the CAPI v1beta2 InfraMachine contract.
- **Architecture invariant:** No RPC between main controller and providers — communication is **CRD-only**. If a design wants HTTP/gRPC between them, it's wrong.
- **Workspace layout:** Cargo workspace. Phase 0 (done) ships `crates/banlieue-api` with two API groups: `banlieue.io/v1alpha1` (`Provider`, `VMClass`, `VMImage`, `VirtualMachine`) and `infrastructure.banlieue.io/v1alpha1` (`VSphereMachine`, `VSphereMachineTemplate`). Phase 1+ adds `banlieue-controller`, `banlieue-provider-sdk`, and `banlieue-provider-{vsphere,proxmox,libvirt}` per the out-of-repo roadmap at `~/dev/roadmaps/banlieue/`.
- **Single binary, library role crates (ADR-0004):** The only executable is `crates/banlieue` (the `banlieue` binary). It just parses a clap subcommand tree and dispatches into the role crates. `banlieue-controller` and every `banlieue-provider-*` are **libraries** (no `main.rs`/`[[bin]]`) that each export a public `Cli` (`#[derive(clap::Args)]`) and `pub async fn run(cli) -> anyhow::Result<()>`. Providers are gated by per-provider features on the `banlieue` crate (`default = ["vsphere"]`; `vcsim` passes through to `banlieue-provider-vsphere/vcsim`). The Deployment selects the role via container `args`.
- **clap pattern for role `Cli`s:** role `Cli` structs derive `clap::Args` (not `Parser`) so they embed as subcommand payloads (`Command::Controller(banlieue_controller::Cli)`). To parse one standalone in a unit test, wrap it: `#[derive(Parser)] struct Wrapper { #[command(flatten)] cli: Cli }` then `Wrapper::parse_from([...]).cli`. See `app_tests.rs` in the controller / vsphere crates.
- **Shared process bootstrap lives in `banlieue-provider-sdk::bootstrap`:** `init_tracing(format, level, extra_directives)`, `serve_health(port)`, `shutdown_signal()`. Per-crate log directives passed as `extra` (`["kube=warn"]` for the controller, `["kube=warn","vim_rs=warn"]` for vsphere). Don't re-implement these in role crates.
- **CRD generation:** `cargo run -p banlieue-api --bin crdgen --features crdgen` — the `crdgen` binary is feature-gated, so the flag is required. `serde_yaml` is also gated on the `crdgen` feature via `crdgen = ["dep:serde_yaml"]`.

- **Test file colocation requires `#[path]`** because `src/foo.rs` is a leaf file-module. Pattern: at the bottom of `src/foo.rs` put `#[cfg(test)] #[path = "foo_tests.rs"] mod foo_tests;`, then put a `mod tests { use super::super::*; ... }` inside `src/foo_tests.rs`. Without `#[path]`, rustc looks for `src/foo/foo_tests.rs`. - **kube-derive's CRD flattener cannot handle serde-tagged enums** (the actual root cause behind the original buglog bug-006). Each variant subschema of a `#[serde(tag = "x")]` enum naturally fixes `x` to a different enum value, but kube-core demands identical schemas for properties shared across subschemas. The CRD-generation panic is therefore fundamental to tagged enums, not a metadata bug. **The correct Kubernetes pattern is a flat struct** with a discriminator-string field plus optional sibling fields per variant. This is how `IpamSpec` was redesigned on 2026-05-25 (bug-006 fixed). Future learning: do not introduce `#[serde(tag = ...)]` enums on any type that needs to land in a CRD.

- **Scheduler shape (Phase 1A iter 2, 2026-05-26):** pure function `crates/banlieue-controller/src/reconciler/scheduler::schedule(vm, class, image, providers, existing_vms) → Result<Decision, ScheduleError>`. - **Backend ID resolution rule (2026-05-26):** when a Provider declares `StorageClassMapping { name: "gold", target: { datastore: "ds-1" } }` (or similar), the scheduler resolves "gold" to a single backend_id string by taking **the first value of the target BTreeMap in lexical key order**. This works for: `{datastore: ds-1}` → "ds-1", `{datastoreCluster: dsc-gold}` → "dsc-gold", `{tagCategory: tier, tag: gold}` → "gold" (because BTreeMap sorts by key, and `tag` < `tagCategory`). If no Provider mapping exists at all the backend_id falls back to the class name itself. The provider's reconciler (Phase 1B+) is the consumer; vSphere takes a single `datastore: String` so this rule produces what it needs.

- **VirtualMachine status-mirror aggregate Ready rule:** `Ready=True` iff `Scheduled=True && (PlacementValid != False) && InfrastructureReady=True`. Reasons when False: `Scheduling` (not scheduled), `PlacementInvalid` (current placement doesn't satisfy spec), `InfrastructureNotReady` (infra not ready), `Reconciled` (success). This is the convention for 1:1 owned infra CRs — keeps the relationship discoverable via `kubectl get vspheremachine <vm-name>` without needing an index. Owner-reference back to the VM has `controller: true, blockOwnerDeletion: true`.

- **[2026-07-31] Two field managers cannot share a `conditions` list.** `Condition` arrays generated by kube-derive/schemars carry no `x-kubernetes-list-type: map` marker, so server-side apply treats the list as one atomic value: two managers writing entries fight over the whole array instead of merging per entry. - **[2026-07-31] RBAC privilege-escalation prevention shapes the operator's ClusterRole.** Kubernetes refuses to let a subject create or bind a Role carrying permissions it does not itself hold, unless it has `escalate` / `bind` on rbac.authorization.k8s.io. - **[2026-07-31] `resourceNames` only constrains verbs that name one object.** Kubernetes ignores it for `list`, `watch`, `create` and `deletecollection` — a rule mixing `resourceNames` with `list` silently grants list over EVERYTHING of that type. - **[2026-07-31] Cluster-scoped dependents cannot be garbage-collected by a namespaced owner.** A ClusterRoleBinding with an ownerReference to a namespaced `Provider` is deleted *immediately* — the GC sees a cross-scope owner as missing. - **[2026-07-31] The kind e2e asserts the OPERATOR's contract, never backend reachability (ADR-0014).** The suite's Provider points at `vcenter.invalid` (RFC 2606 — never resolves), so the spawned provider pod is *expected* to stay NotReady and `status.workload.readyReplicas` *expected* to stay 0. - **[2026-07-31] An e2e that asserts only ABSENCE is worthless without a positive control.** `a_paused_provider_gets_no_workload` passed cleanly on the exact run where the operator was 403ing on everything — "no workload was created" is satisfied by a paused Provider AND by a dead operator, so the test carried zero information. Apply this generally: every "X did not happen" assertion needs a paired "…but X does happen when it should", or it is untestable-by-construction and will silently go green through total breakage.
- **[2026-07-31] A cluster-scoped object needs the NAMESPACE in its name.** banlieue-operator derived every object's name as `banlieue-provider-<class>-<provider>`. That is fine for the namespaced four (their namespace disambiguates them) but wrong for the ClusterRoleBinding: two Providers sharing a name and class in different namespaces collided on ONE object and fought over its subject — each SSA-applying its own namespace, last writer wins, loser silently loses permissions. Installing them from bootstrap would have contradicted an Accepted ADR. - **[2026-07-31] Prune by LABEL, never by a recomputed name.** Cleanup that rebuilds an object name from a CR's *current* spec cannot find objects created under a previous spec — precisely the objects owner references also cannot reclaim. banlieue-operator's cleanup now selects on `banlieue.io/provider` + `banlieue.io/provider-namespace` across all namespaces, because a class change can move the workload namespace too.

- **[2026-09-22] An admission policy that validates a field against `request.userInfo` MUST scope that check to CREATE.** The claim subject policy compared `spec.subject.id` to the authenticated username on CREATE *and* UPDATE — so when the claim controller added its finalizer (an UPDATE, as `kubernetes-admin`), the policy denied it. ### Key Learning (2026-09-21)

- **libvirt carries TWO RPC programs on one connection.** The qemu-specific procedures — `virDomainQemuAgentCommand`, the only route to `qemu-guest-agent` — live in program `0x2000_8087`, not the remote driver's `0x2000_8086`. Framing is identical, so `Session::call_on_program` / `recv_on_program` parameterise it; the desync tripwire in `recv` must be parameterised too or a qemu reply trips a check meant to catch corruption. Verified live: libvirtd answers with a *semantic* error ("domain is not running") rather than a protocol one, which is what proves program number, procedure number and argument encoding are all right.
- **Kairos Ubuntu 24.04 (raw) boots but ships no `qemu-guest-agent`**, so on libvirt it cannot satisfy `GuestReady` at all. An image gap, not a code one. Check with `virsh qemu-agent-command <domain> '{"execute":"guest-ping"}'` before adopting an image for a Deferred pool.
- **A qcow2 overlay over a *raw* backing volume does boot.** Retires the earlier "BackingFile does not boot" suspicion, which was an artefact of that test's upload path (volume declared raw, contents qcow2), not of the shipped pipeline.
- **GitHub is OAuth2, not OIDC** — no ID tokens, no discovery document — so `kube-apiserver --oidc-issuer-url` cannot point at it; Dex bridges it. Two details that cost real time: use ONE issuer URL reachable from browser, kubectl and the apiserver (NodePort + kind host-port mapping, hence an IP SAN not a DNS name — `iss` must match byte-for-byte), and `--oidc-ca-file` needs the CA across BOTH boundaries (kind `extraMounts` host→node AND kubeadm `apiServer.extraVolumes` node→static pod). The apiserver starts fine with an issuer that does not exist yet, so cluster-then-Dex ordering is safe.
